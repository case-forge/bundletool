# Architecture

How the code under `public/js/` is organised. This is for someone changing
the code; for what the tool does and how to run it, see `README.md`. A design
for serving these files under version-stamped names, so they can be cached
for a year, is in `docs/fingerprinting.md`.

The PDF engine is **@cantoo/pdf-lib** (MIT) throughout, the only PDF engine
the application loads. Every module reaches it through one file,
`bundletoolPdfLib.js`, which is the only place a version is pinned.

Storage keys keep the `buntool` prefix rather than `bundletool`: see
*Storage keys are not renamed* below.

## PDF engine and shared primitives

- **bundletoolPdfLib.js**: The single import site for @cantoo/pdf-lib and fontkit, from the self-hosted bundles under `public/js/vendor/` and the site-wide `static/vendor/` (regenerated by `scripts/build-vendor.mjs`; versions pinned in package.json). Nothing loads from a third-party CDN at runtime: `tests/policy.test.mjs` fails if a CDN URL appears.
- **bundletoolPdfLoad.js**: The one way bytes become a document. Opens blank-user-password files (court seals) silently by real decryption, exposes `unlockPdf()` for the password prompt, and never passes `ignoreEncryption` (which yields blank ciphertext pages); recovers damaged files and reports exactly what came back.
- **bundletoolOutline.js**: Document outline (bookmarks), written from ISO 32000-1:2008 §12.3.3. pdf-lib has no outline API and no maintained third-party package provides one.
- **bundletoolLinks.js**: Internal link annotations. Appends to `/Annots`, never replaces it.
- **bundletoolFooter.js**: The page-number footer: white blanking rectangle first, grey plate, text, and a link back to the index. Handles 0/90/180/270 rotation. Writes into its own tagged content stream so it can be removed exactly.

## Backend modules

- **bundletoolMain.js**: Main orchestration logic for bundle creation.
- **bundletoolConfig.js**: Configuration. Data structure and validator for data passed from frontend to backend.
- **bundletoolPages.js**: Input PDF validation, coversheets, page numbering, `rotatePdfBytes` (turns every page of a document, or the pages listed, by a multiple of 90 degrees, added to each page's own rotation) and `imagesToPdf` (one PDF page per picture).
- **bundletoolImages.js**: Photos: reads the format from the bytes, applies EXIF rotation, scales very large pictures down, decodes WEBP, AVIF, GIF, BMP and HEIC (Safari only) through the browser and TIFF through utif2 (`public/js/vendor/utif2.js`, loaded only for a TIFF), and hands back JPEG or PNG pages. `frontend/imageFiles.js` is its front-end side (file to PDF, and the messages for a photo that cannot be used). The accepted list is in the Guide under Accepted files.
- **bundletoolSmallerPhotos.js**: Smaller photos (`pageOptions.smallerPhotos`, on by default): a document BundleTool made from pictures goes into the bundle with each page's one picture at most 2000 pixels on its long edge, as a JPEG at quality 0.85 (a PNG takes whichever is smaller of that and lossless at the smaller size, and any picture that would not come out smaller is left as it is). The picture keeps its name and its place on the page, so the page looks the same and a text layer read from the full picture still lies over the same words. Never enlarges; never sees a PDF that was added as a PDF. The pixel work is a codec: the browser's canvas here, `@napi-rs/canvas` on the command line (`scripts/cliSmallerPhotos.mjs`).
- **bundletoolPdfSafety.js**: what a source document carries beyond its pages: finds unapplied `/Redact` markers when a document is added, and cleans each user document just before it is copied into the bundle (filled forms flattened, internal and named links re-created against the pages they now occupy, every action on an annotation, form field or page is removed unless it is a web, mail or phone link, which is rebuilt with nothing chained behind it; scripts, launch, submit, import, remote-file and media actions, attachments, article threads and associated files are dropped, with a bounded walk of everything reachable from each page as a net). Never runs on the pages the tool draws itself. Tests build a hostile fixture (`tests/fixtures/pdf/active.pdf`, made by `make_fixtures.py`) through the real pipeline and scan every object of the finished bundle (`tests/activeContent.test.mjs`).
- **bundletoolSniff.js**: What a file really is, from its own bytes (PDF, each photo type, zip, older Office, program, web page, text...), and a zip's directory read from its end without unpacking, so a zip bomb is recognised before anything inflates it.
- **frontend/fileGate.js**: The one gate every file passes (Add Documents, drops, the coversheet, a manifest import): decides the type by content, applies the size limits in `frontend/limits.js`, checks a Word document's directory, text length and pictures before conversion, makes names safe to show and store, and words every refusal as what happened, which file and what to do.
- **bundletoolPdfInspect.js**: Page count and size, attachments, portfolios, XFA forms, and streams that unpack to gigabytes, read from a loaded PDF.
- **frontend/dropPosition.js**: Where files dragged in from outside land in the Review Table, and the insertion line.
- **bundletoolMerge.js**: PDF merging. Copies one source document at a time and drops it before opening the next, so peak memory stays at ~(destination + one source).
- **bundletoolToc.js**: Index generation (depends on jspdf and jspdf-autotable).
- **bundletoolCover.js**: The cover page. See *The cover page* below.
- **bundletoolMeta.js**: Index hyperlinks, bookmarks and bundle metadata, all in one parse. The bundle index lives in the PDF Info dictionary under `/BundleIndex`; **do not rename that key**: add-time bundle detection and reopening both find a bundle by it.
- **bundletoolRestore.js**: Opening a bundle back up: one parse for metadata, config and the split. Also `detectBundle()`, which `validateAndCountPages` runs on every added file so a bundle added as an ordinary document is recognised and offered for opening or splitting.
- **bundletoolSplit.js**: The email splitter: divides a finished bundle into parts that fit a 25,000,000-byte message after base64 inflation (~37%), so the default part target is 18 MB of raw PDF, not 25. Cuts on document boundaries read from the embedded index; sizes are measured by actually building each candidate part, never estimated, because scans weigh orders of magnitude more than typed pages. Part covers use built-in Helvetica so they cost bytes, not an embedded family. `mode: 'section'` returns a part for the cover and index and one per section (any part over the target is cut further by size, `subPart`/`subPartCount`); `inspectBundleForSplit()` tells the dialog which sections a bundle records.
- **bundletoolSplitOwn.js**: The email splitter's third labelling style, "an index and page numbers of their own": each part is built as a small bundle (the bundle's cover, an index of only its documents headed "Part N of M" with a "Bundle page" column, the documents, footers renumbered from 1 after the bundle's own tagged footers are removed, index links, footer links, bookmarks and an embedded bundle index so a part can be reopened). Numbering by section is left as it is. **bundletoolSplitLinks.js** holds the link lifting and re-pointing both kinds of part share.

## Workers

Each worker runs in an isolated thread and is terminated after use, freeing
its entire heap. The workers are thin: they carry message plumbing only, and
import the same modules the main thread uses.

- **workers/bundletoolMergeWorker.js**: merge operations.
- **workers/bundletoolFooterWorker.js**: page numbering.
- **workers/bundletoolTiffWorker.js**: decodes a TIFF one page at a time off the main thread (checks in `bundletoolTiff.js`); stopped after 30 seconds without progress.
- **bundletoolTiffStrict.js**: reads PackBits, LZW, Deflate and CCITT fax (Group 3, Group 4, modified Huffman) strips the way the format defines, and checks a JPEG-in-TIFF strip's start, frame, size and end (not its scan data), only to prove they are whole (utif2 reports nothing when a strip is damaged); a page whose data is not whole is refused with "This scan looks damaged: page N could not be read completely". A page that decodes cleanly is never refused, blank or not. Deflate and JPEG strips are not checked. Fixtures: `tests/fixtures/tiff/` (regenerated by `make_fixtures.py`, needs Pillow, not needed to run the suite).
- **workers/bundletoolBuildWorker.js**: the single-pass build: merge, page numbers, hyperlinks, bookmarks and metadata in one worker.

## Frontend modules

- **frontend.js**: Frontend entry point.
- **frontend/crashGuard.js**: Notices when a build did not finish and offers the saved documents back.
- **frontend/coverEditor.js**: The coversheet maker: previews the actual PDF as the fields change (double-buffered iframes, so the preview never flashes blank mid-load), and on confirm writes the fields back to the hidden cover state for the build to draw from. On a browser with no embedded PDF viewer (mostly phones), it says so plainly and the fields still work; `navigator.pdfViewerEnabled` is the check, never UA sniffing.
- **frontend/pageView.js**: One PDF shown a page at a time on a canvas with pdf.js, and its "Page n of N" paging (buttons, a typed page number, the arrow keys): pdf.js reads with no script evaluation, no XFA forms and a ceiling on picture size, only the page shown is held, and the document is freed on close. Shared by the document window and the preview's pictures.
- **frontend/previewPages.js**: Preview Bundle and Preview Index on a browser with no PDF viewer (`navigator.pdfViewerEnabled === false`, most phones): the finished PDF as pictures in the preview window, one page at a time, read-only, with the window's own Save, Split for email and close. Loaded only on such a browser.
- **frontend/rotate.js**: The document window for one Review Table row, opened by the row's eye: pages through the document with pdf.js (`frontend/pageView.js`; only the page shown is drawn), turns it and writes the turn with `rotatePdfBytes`, removes the page shown once confirmed (`removePdfPages` in `bundletoolPages.js`, which leaves nothing of the page in the file), runs Force OCR (`frontend/ocrForce.js`), and shows notes on the page shown (`PAGE_NOTE_CHECKS`: "This page looks blank" comes from `pageInk` in `bundletoolDeskew.js`, "This page looks sideways" from `sidewaysPageNote` in `frontend/ocrReorient.js`). Loaded on first use.
- **frontend/ocrAuto.js**: The automatic OCR check on add. Each document is checked straight away for pages without text of their own (`pagesToRead` in `frontend/bundletoolOcrDocument.js`, no engine), then documents with pages to read are read one at a time, in the order they were added. Skip on a row stops that document alone and the queue moves on; a document changed while it was read is read again; a saved session restored before its reading finished reads it again (`ocrPending`), unless it was skipped (`ocrSkipped`).
- **frontend/ocrReading.js**: What is being read, shared by the automatic check and Force OCR: an entry per document (checking, waiting, reading), pages done of pages to read, Skip, and the estimate (the average seconds per page actually measured on this device in this visit, over the last 8 pages, times the pages left; none before the first page). The row badge (`fileRows.js`), the totals line (`bundleTotals.js`) and the Create Bundle question (`frontend/ocrWait.js`) listen to it.
- **frontend/ocrWait.js**: Create Bundle while text is still being read: asks about one document at a time, the one being read now, with its estimate. Wait waits for it (with progress and Cancel) and then asks about the next, Skip this document stops its reading and asks about the next, Cancel builds nothing; the build starts when nothing is left.
- **frontend/smallerPhotos.js**: The browser's side of Smaller photos: when a bundle is built, each document made from pictures (`convertedFromImage`) is replaced, in the build's copy of the documents only, by its copy with smaller pictures (made once per held file).
- **frontend/ocrReorient.js**: The browser's side of the two optional OCR page settings (Turn sideways scanned pages upright, Straighten tilted scanned pages): reads them for the automatic check and Force OCR, keeps what reading changed on the document's entry (`ocrPages`, and `pagesChanged` when a page was turned or straightened), keeps that record in step when the window removes a page or puts one back as scanned, gives the window its notes (sideways, turned upright, straightened by so much) and the OCR badge its tooltip. The pages themselves are changed in `bundletoolOcrReorient.js`, shared with the command line.
- **frontend/reviewTableHeader.js**: The Review Table's header buttons, Download and Clear All, shown once the table holds a document.
- **frontend/documentDownload.js**: The Download button's picker and output: a section, the documents in no section, only those BundleTool changed, or all of them, as one PDF or a zip in bundle order. Loaded on first use.
- **bundletoolZip.js**: A store-only zip writer (CRC-32, UTF-8 names, no zip64) for the split dialog's "Download zip" and the Review Table's Download.
- **frontend/emailSplit.js**: The Split for email modal: settings in, measured parts out, named `<bundle>-part-1-of-3.pdf` when split by size, and `<Bundle title> - A Applications.pdf` when split by section, saved singly or as one zip. Reached from the bundle-ready overlay and each Recent bundles row.
- **bundletoolTutorial.js**: the on-demand tour. The spotlight is derived from the target's live geometry every animation frame, nothing is precomputed, so Back recomputes exactly like Next and scrolling or reflow cannot detach the highlight.

## The cover page

**The coversheet maker is the one door to a cover.** There is no separate
auto-generate step. *Add Coversheet* opens the
maker (`frontend/coverEditor.js`): live PDF preview, per-firm remembered
defaults (court, statute line, party labels: the labels are configurable
because civil work says Claimant and Defendant), and confirming writes the
fields back to hidden inputs and sets `pageOptions.generateCover`. The build
then draws the cover from config, so a claim number corrected later still
reaches the front page and a reopened bundle comes back editable. Generating
with no cover (or no sections) warns once, naming what is missing, and
continues.

**An uploaded coversheet wins.** The smaller *or add your own* path takes a
PDF, Word document or photo (photos wrap to A4); supplying one discards a
maker design and vice versa. There is never more than one cover page.
`resolveCoverSource()` is the whole rule, in one function, and it resolves
once per build into `pageOptions.coverSource` (`uploaded` / `generated` /
`none`). Everything downstream reads that. `generateCover` must be explicitly
true: silence means none, because covers are opt-in and treating an absent
value as on would draw a cover nobody asked for.

`pageOptions.coversheet` means *there is a cover page at physical page 1*,
and is written back at build time so the offsets that depend
on it agree with what was actually merged: `createTocEntries`' coversheetOffset,
`applyMeta`'s link targets, `indexPageIndex`, and the physical page numbers in
the embedded bundle index.

**Reopening a bundle.** A generated cover is *not* handed back as a file. Its
fields are restored and `generateCover` re-set, so it is redrawn on the next
build and a bundle title corrected after reopening reaches the front page. An
uploaded coversheet comes back as a file. A bundle that records
`coverSource: none`, or no cover setting at all (one made by BunTool, for
example), reopens with no cover: the generate-time warning catches it on its
way back out without one.

**Two designs, three toggles.** `cover.layout` is `classic` or `grid`;
nothing else is a design. The differences a third design would have carried
are settings on both: `cover.caseNumberLine` (on the court's line or its own
line), `cover.partyLabelPlacement` (label under the name, or on its line),
`cover.caseNumberAlign` and `cover.headingAlign` (left, centre or right for
the case number's own line and for the court and subheading) and
`cover.partyAlign` (left, centre or right for the stacked design). The
default cover is the compact one: stacked, the case number on the court's
line, each label on its name's line. Both designs always rule the title,
above and below, with the text equidistant from the rules; `cover.titleLines`
makes each rule a pair of thin ones. A side with several people numbers each
label. The classic layout's heading design, and the footer's plate geometry,
both follow CaseForge's command line bundle tool (BundleToolCLI): court and
case number, `BETWEEN:` with the parties, the title between two rules. Where
the layout departs from that design, and why it leaves out the FL401/C100
recitals, is documented in the module header.

Two costs, both measured:

- The cover is drawn with pdf-lib, not jsPDF, so that it can be rendered and
  checked in the test suite. jsPDF is a browser bundle (`public/js/vendor/jspdf.js`)
  that the Node tests do not run, which is why index layout is untested (the pipeline
  tests use a two-page stand-in for the index), and the front page of every bundle is
  not a good place to repeat that.
- The consequence is that the index font is embedded twice in a finished
  bundle: once by jsPDF for the index, once by pdf-lib for the cover. Fonts are
  embedded in full rather than subset, deliberately (see `NOTICE`), so that adds
  roughly 0.5 MB to a bundle: 501 KB for EB Garamond, 222 KB for Ubuntu Mono.
  On a court bundle of tens of megabytes that is worth paying for a cover page
  that is tested.

## Storage keys are not renamed

`buntool_theme`, `buntool-autosave` (IndexedDB) and `buntool-default-config`
keep their `buntool` names. They name data already sitting in users' browsers;
renaming a key does not migrate the value, it abandons it: saved defaults,
saved documents and finished bundles included. `tests/policy.test.mjs` fails
if any of them changes. Nothing reads `buntool_tutorial_seen` or
`buntool_autosave_welcomed`: the tutorial opens on demand from the header, and
there is no autosave welcome. New keys use the `bundletool_` prefix
(`bundletool_palette` holds the Modern/Classic choice).

## How autosave writes

`buntool-autosave` (IndexedDB, version 3) keeps each document's bytes once, in a `blobs` store, and
each saved copy holds only references to them plus the settings and table order (a few KB). A save
after a small change therefore writes almost nothing. One starts at once when a document is added,
turned, removed or reordered (changes within 250 ms of a save beginning share the next one), and
1.5 s after typing stops. Documents no saved copy refers to are collected under a lock shared by
every tab. While a save is pending or running and there are documents in the table, leaving the
page asks first (`isSavePending` in `bundletoolAutosave.js`); when nothing is pending it never does.
A saved copy that holds its documents' bytes inline loads too.

## One accent

Every accent colour (links, "On" labels, toggle fills, sliders, segmented buttons, hover tints,
focus rings) reads the tokens at the end of `assets/css/bundletool.css`: `--bt-ink` (text and icons),
`--bt-ink-hover`, `--bt-fill`, `--bt-fill-hover`, `--bt-tint` and `--bt-line-soft`. They rest on the
palette's `--color-accent-*` scale, which is the navy in Classic and Modern light and the orange in
Modern dark, so a control cannot take a shade of its own. Templates and scripts use the semantic
classes (`bt-link`, `bt-text-link`, `bt-ink`, `bt-hover-ink`, `bt-hover-tint`, `bt-hover-line`,
`bt-line-soft`, `bt-accent`, `bt-focus-ring`), never a Tailwind blue. `tests/noLegacyBlue.test.mjs`
fails if a blue utility, a `--color-blue-` reference or a raw Tailwind blue hex returns.
